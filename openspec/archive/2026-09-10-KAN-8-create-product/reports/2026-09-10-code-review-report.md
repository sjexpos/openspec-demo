## Assessments requested in the review brief

**Layering discipline — clean.** `ProductController` genuinely contains zero business logic: it builds
a command, delegates, and maps the result; it holds no repository and depends only on the
`ProductService` interface (DIP). `ProductServiceImpl` genuinely owns all three invariants. No
`@Transactional` leaks into presentation, and exactly one exists in the slice, on the impl method
(D6). `CreateProductCommand` genuinely carries no `jakarta.validation` / `io.swagger` dependency, so
the Clean Architecture direction is preserved as D3 promised.

**`resolveOrNotFound`'s generic signature — sound.** `private <T> T resolveOrNotFound(JpaRepository<T,
Long> repository, Long id, String referenceName)` infers `T` from the repository's type argument, and
the assignment target makes any cross-type mistake a compile error (`Unit formatUnit = resolveOrNotFound(brandRepository, …)`
will not compile). Two nits: hardcoding `Long` as the ID type couples the helper to the codebase-wide
convention (acceptable, and `ddl-auto: none` holds); and the `(id, referenceName)` pair is *not*
compiler-checked, so `resolveOrNotFound(unitRepository, command.formatUnitId(), "ContentUnit")` would
compile silently — mitigated in practice because `ProductServiceTests` asserts each of the seven
messages exactly.

**`ProductServiceImpl.create`, line by line — no logic error found.** The three-guard sequence matches
D1 exactly: `existsByOcpc` → seven resolutions in request declaration order → `Objects.equals`
taxonomy check → single `save`. `Objects.equals` correctly avoids NPE/unboxing on either id.
Optional attributes are copied verbatim into the builder with no `orElse`, no `Boolean.TRUE.equals`
and no defaulting, so R6's null-vs-false distinction holds by construction. One theoretical
robustness note: `subcategory.getCategory()` is dereferenced without a null check; this is safe
because `subcategories.category_id` is `NOT NULL` in `V0.1.0`, but it is an unchecked assumption
about the schema rather than an enforced one.

**`existsByOcpc` + `@SQLRestriction` — correct and genuinely pinned.** `ProductRepositoryTests`
includes `existsByOcpc_when_onlyOcpcHolderIsSoftDeleted_returnsFalse` and
`delete_when_called_keepsRowPhysicallyPresent`, so both halves of D7 survive future mapping changes.

**Taxonomy check against the LAZY `Subcategory.category` proxy — correct *and proven*.**
`ProductReferenceDataRepositoryTests.getCategory_when_subcategoryPersisted_returnsParentIdWithoutInitialisingProxy`
asserts `assertEquals(persistedCategory.getId(), reloaded.getCategory().getId())` **and**
`assertFalse(Hibernate.isInitialized(reloaded.getCategory()))`. D12's "zero extra queries" claim is
therefore not an assumption — it is a pinned invariant. This directly mitigates a documented risk and
is the single strongest piece of test work in the change.

**W2's security angle — refuted.** The brief asked whether an unbounded `ocpc`/`title` could surface
as a raw 500 / `DataIntegrityViolationException` with leaked internals. It cannot:
`V0.1.0__initialData_SM.sql:207-208` declares both columns as **unbounded** `varchar`, so PostgreSQL
performs no length check and no truncation error is reachable even if the `@Size` constraints were
deleted entirely. W2 is a regression-safety gap, not a vulnerability. (The genuine unbounded-input
concern is `description` — see m3.)

**The `HttpMessageNotReadableException` handler (D9) — cannot be used to probe internal state, and
is a net security improvement.** The message is a hardcoded string; `ex` is accepted but never read,
so nothing about the parser, offset, payload or SQL layer escapes. It also incidentally closes a real
500: an out-of-`int`-range JSON number for `thc`/`cbd`/`formatValue`/`contentValue` raises a Jackson
`InvalidFormatException`, which is a `HttpMessageNotReadableException` subclass and now yields 400.
The cross-cutting effect on existing endpoints is properly regression-tested in
`BrandControllerEndpointsTests` and `DispensaryEndpointsTests`.

**Disclosed deviations — well contained, with one leak.** D2 (object associations to `Brand`/`Strain`)
holds its guard rails: no `CascadeType`, no `orphanRemoval`, all `LAZY`, no inverse collections, and
no setter is ever called on a resolved reference — so the create transaction stays single-aggregate.
D14 is applied consistently to `Product` and `Strain` and matches the lookup-entity precedent (its
only leak is the cosmetic warning in m2). D3 is the one deviation that **does** leak inconsistency:
the command side is a named builder, the response side is 18 positional arguments (see the Question
row). D15's reasoning (the taxonomy invariant sits in the service because `DomainException` lives in
the application layer) is a real Clean Architecture constraint, honestly argued, with the correct
follow-up recorded.

**DRY.** `resolveOrNotFound` is a textbook correct application (seven instances, private to its one
consumer, rule-of-three satisfied twice over). `StrainReferenceDataFixtures` is correctly narrow, and
its own Javadoc cites the anti-over-DRY guidance. `ProductEndpointsTests` re-implements strain seeding
rather than reusing that fixture, but this is structurally forced (`StrainReferenceDataFixtures` takes
a `TestEntityManager`, unavailable under `@SpringBootTest`) and is consistent with the dry-principle
skill's "some duplication in test setup is acceptable". No DRY defect found.

- **W3 (the "90% coverage gate" claim): correct the gate, not the claim.** The 90% threshold

  m1, still not a blocker, still not a regression.

## Status

**FAIL** — blocking on test adequacy, not on behaviour.

To be unambiguous about what this verdict does and does not say: **no functional defect, no security
vulnerability and no spec-behaviour violation was found in the delivered code.** The implementation
is correct as written, the layering is clean, the disclosed deviations are well contained, and 108
tests pass in a fresh run this agent performed. The build is green end to end.

The two Major findings are that the suite cannot *prove* two of the spec's own scenarios:

1. R1 / *"Created product echoes the submitted attributes"* requires the response to report "for
   every accepted attribute" the persisted value. Three of eighteen attributes are asserted, and I
   demonstrated experimentally that a wrong reference id in the response passes the whole suite.
2. R2 / *"Required field present but invalid"* names the `ocpc`/`title` length bounds normatively;
   they have no test instance anywhere.

Archiving in the current state would lock in a green suite that is demonstrably blind to a wrong
response payload on the change's only endpoint, in a change whose own project mandates TDD, 90%
coverage and boundary-value tests. Every finding is closeable in one focused pass: roughly four new
tests, two one-line code touches, one pom binding, and the artifact corrections already queued for
verify's W1.
