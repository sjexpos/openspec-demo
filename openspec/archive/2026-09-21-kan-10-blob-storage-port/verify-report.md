## 5. Correctness review (code-auditing lens)

| Check | Finding |
|---|---|
| `isCanonicalKey` null/blank/traversal | Correct: null→false; blank/traversal fail prefix+suffix match. `RANDOM_PART.matcher(suffix).matches()` requires full 32-hex match — no partial-match bug. |
| Key entropy | `UUID.randomUUID()` minus dashes = 122 bits, lowercase hex — matches `[0-9a-f]{32}` by construction. |
| `remove` atomicity on validation failure | Correct: full pre-validation loop before first `deleteObjects`; mixed-set test proves no store call. |
| Chunking arithmetic | Correct: `from += 1000`, `subList(from, min(from+1000, size))`; boundary tests 1000/1001 pin it. |
| `errors()` handling | Correct: every `errors().key()` collected per chunk; non-empty → warn + throw with immutable `failedKeys`. No silent-data-loss path. |
| Partial-failure throw inside chunk loop | Aborts remaining chunks on first failing chunk — fail-fast, acceptable; caller retries full set idempotently. Not a defect. |
| Exception messages | Carry key / failed keys only; URL never interpolated (`presigned.url()` used only for the return value). Confirmed by test + inspection. |
| `BlobStorageException` immutability | `Set.copyOf` in both `failedKeys` constructors; default `Set.of()`. Getter returns the immutable instance — SpotBugs `EI_EXPOSE_REP2` is a false positive here (see WARNING-1). |
| `Assert.notNull` / `Assert.isTrue` → `IllegalArgumentException` | Correct per Spring contract and spec. |
| `expiresAt` via `Instant.now()` (no `Clock`) | Per locked decision D5/YAGNI; tolerance-window test (±30 s) is robust, not flaky. |
| Thread-safety / state | Adapter is stateless (`final` injected deps, no mutable fields); `pending` is method-local. Safe as singleton `@Component`. |
| Dead code / duplication | None found: prefixes defined once (DRY); no hardcoded regex second copy; no unused imports in new files; `canonicalKeys(count)` overload delegates. |

### SUGGESTION

- **SUGGESTION-1 — Partial-chunk failure aborts remaining chunks.** On `errors()` non-empty in chunk *k* of *n*, chunks *k+1…n* are never attempted and their keys are absent from `failedKeys`. This is fail-fast and idempotent-retry-safe, so it is correct, but callers doing large deletes should be aware a retry must resubmit the full set. Consider documenting this in the `BlobStorage.remove` Javadoc (spec-update-first if pursued).
