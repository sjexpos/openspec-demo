## Why

KAN-10 delivered the storage half of the asset pipeline (`BlobStorage` port + `S3BlobStorageAdapter`): a caller can mint a presigned `PUT` target for `BlobType.BRAND_IMAGE` and upload bytes to `brands/images/<32 hex>`, but nothing records that the blob exists. `brand_images` is a bare `(id, brand_id, image_url)` table with no entity, no repository and no lifecycle. A presigned upload is a two-phase commit across two systems (S3 and Postgres) with no shared transaction — without an intent record written before the upload and a confirmation after it, every asset story re-invents orphan handling, exactly the risk KAN-10 logged as open assumptions 8.3 (who calls `remove`, and when) and 8.4 (orphan blobs have no reclamation). This change delivers the persistence half as a foundation slice — entity, shared lifecycle enum, migration, repository and tests, no endpoint, no service — and establishes the reusable template for the four queued asset stories (`brand_videos`, `strain_images`, `product_images`, `dispensary_images`).

## What Changes

- Add `AssetStatus` enum (`domain/models`) with exactly three constants in order `PENDING`, `UPLOADED`, `DELETED`, owning its legal transitions (`PENDING → UPLOADED`, `PENDING → DELETED`, `UPLOADED → DELETED`; `DELETED` terminal, self-transitions and null targets rejected) plus `isTerminal()` and `isVisible()` (only `UPLOADED` is visible). Resource-agnostic by design: the next asset table reuses it with zero changes.
- Add `BrandImage` entity (`domain/models/brand`): `@Table(name = "brand_images")`, extends `BaseEntity`, `LAZY @ManyToOne Brand`, immutable unique `imageKey` (`image_key`, `updatable = false`), `status` (`@Enumerated(EnumType.STRING)`, no public setters — state changes only via `markUploaded()` / `markDeleted()` which enforce the enum's transition rules). Sole sanctioned creation path is the `pending(brand, imageKey)` factory: sets `PENDING` and rejects any key that is not a canonical `BRAND_IMAGE` key (`brands/images/` + 32 lowercase hex chars), so a `STRAIN_IMAGE` key can never be filed under a brand.
- Add `BrandImageRepository` (`domain/repositories`, `JpaRepository<BrandImage, Long>` consistent with `BrandRepository`/`ProductRepository`) with three queries: `findByBrandIdAndStatus`, `findByImageKey`, `existsByImageKey`. No physical-delete path: removal is represented solely by `status = DELETED`; no `@SQLDelete` / `@SQLRestriction` on the entity (a second "is it deleted?" flag would drift from the status).
- Refactor `BlobType` (behaviour-preserving, DRY): extract per-type `isKeyOf(String)` from `isCanonicalKey`; the global predicate delegates to it. Existing `BlobTypeTests` must pass untouched.
- Add Flyway migration `V0.1.1__brand_images_asset_lifecycle.sql` (`flyway/release_0.1/`, picked up by both Maven plugin and test classpath with no config change): rename `image_url` → `image_key` (safe: no seed rows in `V0.1.0`, no `src/` reference); add `status varchar(16) NOT NULL` with `CHECK (status IN ('PENDING','UPLOADED','DELETED'))` (`varchar` + `CHECK`, not a native PG enum — diffable, reversible, extendable); add `BaseEntity` audit columns (`created_at` default `now()`, `created_by`, `modified_at`, `modified_by`, `deleted_at`, `deleted_by`; `deleted_at`/`deleted_by` exist only because `BaseEntity` maps them and stay unused — status is the delete marker); drop the `status` default after backfill so a forgotten assignment fails loudly; add unique index on `image_key`, composite index on `(brand_id, status)`, and a partial index on `created_at WHERE status = 'PENDING'` for the future orphan sweeper (`PENDING` + `created_at < now() - ttl` stays proportional to orphan count, not table size).
- Docs: update `docs/data-model.md` (*Brand Images* section + ER diagram: `image_key`, `status`, audit columns) and `docs/backend-standards.md` (register the enum-persistence convention: `@Enumerated(EnumType.STRING)` + `varchar` + `CHECK`, never ordinals, never native PG enums).
- Out of scope (follow-ups F1–F7, not built here): any HTTP endpoint; any application service or `PATCH`/confirm flow performing `PENDING → UPLOADED`; applying `AssetStatus` to other asset tables; orphan-reclamation sweeper and `DELETED`-row blob-removal job; ordering/primary-image flags; authentication/authorization (absent codebase-wide).

## Capabilities

### New Capabilities

- `asset-lifecycle`: shared lifecycle of any persisted asset reference pointing at a blob in object storage — exactly three states (`PENDING` = recorded before upload confirmation; `UPLOADED` = confirmed, the only client-visible state; `DELETED` = retired tombstone, blob may still exist), exactly three legal transitions with `DELETED` terminal, text-name persistence contract (DB rejects any other value; renaming a state requires a data migration), reusable by every asset resource without modification.

### Modified Capabilities

- `brands-management`: brand images become a first-class entity mapped to `brand_images` (audit base type, brand reference, canonical `BRAND_IMAGE` blob key — never a presigned URL — immutable and unique, created only as `PENDING`); physical deletion of brand image rows is forbidden, removal is `DELETED` only.
- `blob-storage`: extend the blob-type-to-prefix mapping with a per-blob-type canonical-key check (`isKeyOf`) that is true only when a key is canonical **and** carries that type's prefix, derived from the same prefix definitions as the global `isCanonicalKey` predicate.

## Impact

- **Code**: three new domain files (`AssetStatus`, `BrandImage`, `BrandImageRepository`), one behaviour-preserving `BlobType` refactor, one Flyway migration, four test files (new `AssetStatusTests`, `BrandImageTests`, `BrandImageRepositoryTests` against real Postgres + Flyway with `ddl-auto: validate` parity check; extended `BlobTypeTests`). No service, controller, DTO or `GlobalExceptionHandler` change — the slice stops at the domain boundary. DDD: the entity protects its own invariants (guarded transitions, `AccessLevel.NONE` setters); transition table lives in the enum as single source of truth (DRY, KAN-10 precedent); no framework leakage into `AssetStatus`.
- **Database**: `V0.1.1` applies on top of `V0.1.0` (rename + add-column path) and on a fresh DB; Hibernate `validate` passes with zero drift. `brand_images` writes stay single-row inserts/updates by PK; reads are index-backed; `varchar(16)` + `CHECK` costs one bounded comparison per write.
- **Security**: no presigned URL is ever persisted (only the opaque key — URLs are bearer capabilities per KAN-10); key provenance validated in the domain (no path traversal, no cross-resource keys); audit columns owned by `BaseEntity`/`AuditingEntityListener`, never accepted from outside; `DELETED` tombstones keep removal auditable; associations `LAZY`, no inverse collection on `Brand` (no N+1, no unbounded load).
- **Assumptions carrying risk**: (1) rename safety must be re-confirmed if any environment was seeded manually; (2) public-URL derivation (`BlobStorage.urlFor(key)` or CDN base) is owned by the future read story; (3) `BaseEntity` redundancy (`deleted_at` unused) vs a split into `AuditableEntity` + `SoftDeletableEntity` (F6); (4) brand soft-delete does not cascade to images in this slice (`@SQLRestriction` proxy caveat needs a product decision before the delete endpoint); (5) the `PENDING → UPLOADED` confirmation model (`PATCH` vs S3 → SQS notification, whose filter is `products/`-only today) must be decided at refinement of the next story; (6) no auth exists codebase-wide; (7) three states suffice — adding `FAILED`/`EXPIRED`/`REMOVED` later touches every asset table's `CHECK`; (8) blob still exists after the tombstone until F4 ships; (9) no ordering/primary-image concept yet.
